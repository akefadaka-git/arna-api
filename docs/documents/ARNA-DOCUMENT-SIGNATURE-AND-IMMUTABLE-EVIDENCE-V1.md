# ARNA formal document signature and immutable evidence contract

Status: A3.3.2 implementation contract. This document describes the exact verification boundary; it is not a claim that production signing keys have been provisioned.

## 1. Cryptographic profile

- Algorithm: Ed25519 detached signatures, using PHP's native Sodium extension.
- Private keys: generated and retained by the authorized signatory outside ARNA. ARNA never stores or receives a private key.
- Public keys: tenant-scoped rows in `document_signing_keys`. A key is trusted only when an Owner-controlled provisioning process inserts its public key, signer account, validity start, optional expiry and non-empty trust reference.
- Revocation: append a row to `document_signing_key_revocations`. Key records and revocation records are database append-only. A revoked key is rejected even if the signature timestamp predates the revocation.
- Key identifiers are unique within a tenant. The verifier also requires the key to belong to the authenticated signer and the same tenant.

There is intentionally no public key-registration endpoint in this stage. Do not seed, trust, or enable a production key until its identity and custody have been independently verified and Owner-authorized. Test fixtures generate ephemeral keys and are never production trust anchors.

## 2. Canonical signed challenge

The signatory signs the UTF-8 bytes of this JSON object, with the exact property order shown, no whitespace added, and JSON flags `JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE | JSON_THROW_ON_ERROR`:

```json
{
  "contract": "ARNA-DOCUMENT-SIGNATURE-V1",
  "tenant_id": 123,
  "workflow_uuid": "workflow UUID",
  "file_sha256": "64 lowercase hexadecimal characters",
  "signer_user_id": 456,
  "signed_at": "2026-11-18T12:34:56Z"
}
```

The actual values must be the server-issued tenant ID, workflow UUID and SHA-256 of the sealed immutable binary, the authenticated signing user's ID, and a UTC ISO-8601 instant. The PHP implementation exposes this deterministic encoding through `SodiumDocumentSignatureEvidenceVerifier::canonicalPayload()`.

The transition evidence shape is:

```json
{
  "signature_evidence": {
    "key_id": "tenant-registered-key-id",
    "signature": "base64-encoded-64-byte-Ed25519-signature",
    "signed_at": "2026-11-18T12:34:56Z"
  }
}
```

The service decodes the signature strictly, checks Ed25519 key/signature lengths, resolves the tenant + signer + key identifier against the trusted registry, checks validity and revocation, then calls `sodium_crypto_sign_verify_detached`. Invalid, unknown, expired, revoked, future-dated or wrong-signer evidence fails closed before number allocation.

The signed payload binds the exact document bytes and workflow identity. The canonical document number is generated by ARNA inside the issuance transaction; it is not a caller-provided signature claim. If a future product requirement demands the canonical number itself be inside the signed PDF bytes, the number must first be reserved and the final rendered PDF signed; that is a separate protocol revision, not an undocumented change to V1.

## 3. Immutable binary snapshot

On submission, ARNA reads the selected tenant-scoped File Management version and seals a content-addressed snapshot under `document-evidence/{tenant_id}/{sha256}` on the configured local evidence disk.

- The object is created via an exclusive temporary file and atomic no-overwrite hard link.
- A second capture of the same File Management version is accepted only if its bytes produce the same SHA-256 and size. A same-version mutation is rejected; a new File Management version is required.
- `document_file_versions` records tenant, source file/version, evidence disk/path, SHA-256, size, capture actor and instant. MySQL and SQLite triggers reject UPDATE and DELETE.
- Issued documents reference the immutable version row, the signature evidence row, and the same SHA-256.
- Issuance re-hashes the immutable object before it can create an issued record. A missing or changed object fails closed.

This implementation deliberately fails closed for evidence disks that do not expose local filesystem paths and atomic no-overwrite semantics. Do not configure an object-store disk until a provider adapter with conditional create/write-once semantics and independently verified retention controls is implemented. Read-only file permissions are defense in depth, not a substitute for storage-administrator controls, backups or WORM retention.

## 4. Atomic issuance transaction

The `issue` transition no longer accepts an `issued_document_id`. In one database transaction it:

1. locks the workflow and verifies its expected revision/state and governed `documents.issue` authority;
2. locks and validates the immutable file-version row and re-hashes its stored binary;
3. verifies the authenticated signatory's Ed25519 evidence;
4. resolves the full Ethiopian Calendar year at the issuance instant in `Africa/Addis_Ababa`;
5. calls the existing `DocumentNumberAllocator` for the tenant + EE + DD + TT + YYYY scope;
6. inserts the immutable signature evidence and the issued `documents` row, including canonical number, source file/version/hash, immutable evidence ID and signature evidence ID;
7. appends the issued document lifecycle event, advances the workflow revision and appends the workflow event.

Any database failure rolls back the document, signature evidence, counter increment, lifecycle event and workflow transition together. A filesystem snapshot may remain as an unreferenced content-addressed object if a submission transaction fails; it cannot be mistaken for an issued document and may be garbage-collected only by a separately governed retention process.

## 5. Operational gates

Before production use:
- provision the Ed25519 trust anchor through an independently reviewed Owner-controlled process;
- verify signer identity and private-key custody out of band;
- configure the evidence disk as a dedicated local filesystem with restricted write access, backups and monitored integrity;
- independently test restore and tamper detection;
- do not deploy or run production migrations without separate A5 approval.
