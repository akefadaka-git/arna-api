## Decisions and scope

1. **Reuse existing RBAC.** Grant creation, listing and revocation require the existing tenant-scoped `governance.body.manage` permission through `AuthorizationService`. No parallel role/permission engine is introduced.
2. **Narrow scope.** Every grant is bound to exactly one validated tenant, governance body, position, canonical Person/account, action, and inclusive calendar-date interval. A body-wide or cross-body grant is not supported.
3. **Canonical identity.** The grantee and grantor must each resolve to a non-deleted, active `Person` linked to an active `User` account. Membership eligibility is verified through that canonical Person's unique account link and the existing membership `user_id` field. No new identity registry or membership backfill is introduced.
4. **Eligibility and expiry.** A grantee must have an active membership in the same tenant/body/position covering the whole grant period. Grants cannot be backdated. The end date is inclusive; null means open-ended only when the membership is also open-ended.
5. **Separation of duties.** Self-delegation is denied. A delegated membership manager cannot update their own membership. Position-definition changes remain administrator-only. Delegation is not re-delegable; only an actor with the existing RBAC permission may create or revoke grants.
6. **Revocation and provenance.** Grants are not hard-deleted by this service. Creation retains grantor Person, creator account, action, scope, dates, reason and timestamps. Revocation retains revoker account, timestamp and reason. All writes use database transactions and row locks where state changes occur.
7. **Fail closed.** Missing/mismatched tenant context, unknown action, inactive account/person, expired/revoked grant, wrong scope, absent current membership, or malformed date denies authorization.
8. **No invented financial policy.** Financial approvals, amounts, currencies, thresholds, escalation/override, quorum/voting, cross-scope inheritance, meetings/resolutions, and grant chaining remain out of scope pending explicit Owner policy.

## Action catalogue

The initial catalogue is intentionally restricted to:
- `governance.appointment.manage`
- `governance.membership.manage`

The grant is an additive, position-scoped path for updates to existing appointment or membership records. Existing RBAC permission checks remain the first path. Appointment/membership create routes continue to require their existing permission. Lifecycle activation/revocation is not delegated by this slice because the current HTTP controller does not expose distinct transition abilities.

## Persistence and API

- Table/model: `governance_authority_grants` / `GovernanceAuthorityGrant`.
- Service: `GovernanceAuthorityGrantService`; centralizes tenant validation, permission checks, eligibility, date bounds, grant/revoke, and grant lookup.
- API: `GET /api/governance/authority-grants`, `POST /api/governance/authority-grants`, and `DELETE /api/governance/authority-grants/{id}`.
- Existing appointment and membership update policies consult the service only after the existing RBAC check fails and only for a matching position/action. The membership policy explicitly denies the delegated path for the grantee's own record.
- The table stores grant/revocation provenance. There is no automatic historical backfill and no production migration run as part of this change.
