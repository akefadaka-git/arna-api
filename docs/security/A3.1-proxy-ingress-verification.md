# A3.1 — Plesk / reverse-proxy ingress verification checklist

**Purpose:** verify that the deployed ingress boundary cannot let a client-supplied forwarded host select another ARNA tenant. This checklist is an evidence record template; it is not proof that the live host has been inspected.

## Preconditions
- [ ] Identify the production API hostname and the exact Plesk subscription / web-server vhost serving it.
- [ ] Identify every proxy/load-balancer hop between the public client and PHP-FPM/Laravel.
- [ ] Record the actual source IP/CIDR of each trusted proxy hop. Do not assume RFC1918 ranges are correct merely because the application currently lists them.
- [ ] Confirm the origin application cannot be reached directly from the public internet while bypassing the intended ingress.
- [ ] Capture the active Nginx/Apache/Plesk proxy directives and relevant PHP-FPM upstream configuration, with secrets and unrelated customer data redacted.

## Required ingress properties
- [ ] The first trusted edge removes or overwrites any client-supplied `Forwarded` and `X-Forwarded-*` headers before adding its own canonical values.
- [ ] `X-Forwarded-Host` is either not forwarded to the application or is overwritten with the validated public host; it is never copied from an untrusted client.
- [ ] The application trusts forwarded headers only from the actual proxy source addresses. The trusted ranges configured in Laravel match the deployed topology exactly.
- [ ] The public `Host` header is validated against the intended API hostnames at the edge; unknown hosts are rejected.
- [ ] TLS termination and `X-Forwarded-Proto` behavior are consistent, so secure-cookie behavior does not require trusting a client-supplied value.
- [ ] Duplicate, comma-separated, malformed, and conflicting forwarded-host values are rejected or normalized at the edge; they cannot influence tenant resolution.
- [ ] No alternate listener, origin IP, staging hostname, or fallback vhost bypasses these controls.

## Controlled negative test (staging first)
- [ ] From an external client, send a request to tenant A's hostname while supplying `X-Forwarded-Host: tenant-b.maalearna.com.et`.
- [ ] Repeat with `Forwarded: host=tenant-b.maalearna.com.et`, duplicate forwarded-host headers, comma-separated values, and an unrelated unknown host.
- [ ] Confirm the application observes tenant A's validated origin host and never resolves tenant B from the injected value. Use a non-sensitive health or diagnostic endpoint; do not use another tenant's data.
- [ ] Confirm unknown public `Host` values are rejected at ingress.
- [ ] Confirm the request's effective client IP and HTTPS scheme remain correct after proxy normalization.
- [ ] Repeat from an untrusted source that attempts to connect directly to the origin; confirm the connection is blocked.

## Evidence required for closure
- [ ] Dated export or screenshots of the active Plesk vhost / reverse-proxy configuration, with sensitive values redacted but proxy addresses and header directives visible.
- [ ] Proxy-hop diagram listing each hop, source CIDR, and header mutation behavior.
- [ ] Timestamped request/response evidence for the negative tests above, with tokens, cookies, personal data, and tenant data removed.
- [ ] Confirmation of the deployed application commit SHA and matching `TrustedProxyPolicy` implementation.
- [ ] Independent reviewer records whether each required property passed, failed, or could not be observed.

## Failure handling
If any check fails or cannot be evidenced, keep A3.1 open. Correct the edge configuration in a controlled maintenance window, rerun the negative tests, and retain before/after evidence. Do not compensate by trusting all proxies or enabling `X-Forwarded-Host` in Laravel. Do not run production migrations or deploy application changes as part of this verification checklist.
