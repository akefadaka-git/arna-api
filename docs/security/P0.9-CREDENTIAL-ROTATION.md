# P0.9 — Compromised seeded-credential response

## Finding

The former seeder implementation assigned one shared bootstrap password to the two platform administrator accounts and the seeded shareholder cohort. That value was present in public repository history and was printed by the core seeder, including CI output. Treat it as compromised. Do not reuse it.

Removing the value from the current source does not remove it from Git history, prior workflow logs, forks, caches, or downloaded artifacts.

## New-account behavior

- New administrator and shareholder accounts receive independent 64-character random credentials which are hashed immediately.
- Plaintext credentials are not returned, stored, printed, or sent to logs.
- Existing persisted rows retain their current password when a domain seeder updates them in place. The full `MasesCoreSeeder` flow is intentionally destructive: it clears and recreates the seeded user cohort, so each recreated account receives a fresh random credential.
- Users must establish access through the normal password-reset flow. Confirm that the target environment has working outbound mail and that account email addresses are controlled by the intended users before relying on that flow.

## Identify and rotate accounts in an environment

The command `arna:rotate-compromised-bootstrap-credentials` compares the supplied incident credential against stored password hashes. The credential is read only from the process environment variable `ARNA_COMPROMISED_BOOTSTRAP_PASSWORD`; it is never emitted by the command.

1. Set `ARNA_COMPROMISED_BOOTSTRAP_PASSWORD` in the target environment's protected process environment. Do not place its value in a command-line argument, source file, ticket, or shell history.
2. Run `php artisan arna:rotate-compromised-bootstrap-credentials` first. This is a dry run and reports only the number of matching accounts.
3. Confirm the affected accounts and verify that their password-reset email path is operational.
4. Run `php artisan arna:rotate-compromised-bootstrap-credentials --apply` during an approved maintenance window. The command replaces each matching password with an independent random value, rotates the remember-me token, and deletes that user's Sanctum personal access tokens.
5. Remove the temporary environment variable after the operation. Confirm users can complete password reset and sign in with their newly established credentials.

The command is idempotent for this incident credential: after a successful rotation, the newly generated hashes no longer match it.

## Limits and required operational follow-up

- The command has not been run against production or any live customer database. No production account or token rotation is claimed.
- It revokes Sanctum personal access tokens and invalidates remember-me cookies. It does not guarantee invalidation of already-authenticated browser sessions, third-party sessions, or credentials copied outside the application. Review and invalidate those separately where applicable.
- Verify account ownership and mail delivery before rotation; random replacement credentials are intentionally unrecoverable.
- Public Git history and previously generated CI logs may still contain the former credential. After credential rotation, assess log retention/deletion and plan any history rewrite as a separately reviewed repository-maintenance operation. Do not rewrite shared history as part of this PR.
- Do not merge or deploy this change without separate Owner approval.
