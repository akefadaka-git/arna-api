## 1. Purpose and decision boundary

This document establishes the evidence baseline and implementation controls for Phase 1. It does not claim that all future capabilities exist or are production-ready. It is a candidate control document pending Owner review.

Phase 1 will implement and integrate bounded end-to-end capabilities in dependency order. Existing capabilities must be reconciled and extended where appropriate; new domains must not be duplicated merely because their implementation is not obvious from a top-level directory inventory.

No production database operation, deployment, destructive action, repository setting change, or merge is authorized by this document. Each implementation package requires an explicit scope and gate decision.

## 4. Known risks and open evidence

### R1 — True concurrent repayment behavior (OPEN)

The merged PR #5 does not prove concurrency safety. Sequential feature tests, including tests executed using SQLite, cannot establish MySQL row-lock behavior under overlapping requests.

**Required evidence:** an isolated MySQL test using independent processes or connections and committed shared fixtures, synchronized to create real overlap. At minimum, test same-key/same-payload replay, same-key/different-payload conflict, distinct-key repayments against one loan, and failure/rollback behavior. Assert persisted payments, allocations, loan settled/outstanding values, obligation balances, and relevant ledger/wallet totals after workers finish.

Do not claim this risk closed until the test establishes overlap and passes on the candidate revision.

### R2 — Migration discovery and ownership (OPEN)

Historical documentation states that root `database/migrations/` is the authoritative flat migration directory. The current repository tree also contains domain-specific migration files. Before adding migrations, inspect Laravel migration registration, provider bootstrapping, path discovery, duplicate migration names, and clean-install behavior.

**Rule:** do not relocate existing migrations, create a second migration authority, or assume nested migrations are loaded without verifying the actual runner behavior.

### R3 — Identity and unified People Profile contract (OPEN)

The person, user account, login identifier, shareholder/employee profile, contact point, and scoped role assignment must remain conceptually distinct. Inspect current models and schema before choosing a canonical model. Do not create duplicate people records or silently change login uniqueness semantics.

**Required design:** entity relationships, identifier normalization/uniqueness, verification and revocation lifecycle, multiple permitted roles, tenant scope, data retention, and authorization boundaries.

### R4 — Branch governance (RECOMMENDATION)

Repository metadata returned `protected: false` for both `main` branches during the baseline inspection. No repository settings were changed.

**Recommendation:** Owner-approved branch protection and required CI checks should be considered before high-impact implementation merges. This document does not authorize changing repository settings.

### R5 — Integration candidates (OPEN)

An existing API integration-reconciliation plan recommends against merging a large inventory PR as one unit and calls for bounded candidate branches with explicit diff/dependency/test evidence.

**Rule:** review source candidates individually. Do not wholesale merge a large branch, duplicate the same paths across integration units, or override current main behavior without a specific comparison and acceptance gate.

### R6 — Production readiness (NOT ESTABLISHED)

The successful workflows cited here are not a production deployment, backup-restore drill, full threat model, complete performance test, or proof that every business flow is ready. No production database operation or deployment was performed for this baseline.

## 7. Vertical-slice implementation standard

Every implementation item must include all applicable elements below in one bounded candidate:

1. Requirement and explicit out-of-scope statement.
2. Domain model/state transitions and data ownership.
3. Migration and database constraints, if needed.
4. Domain service and transaction behavior.
5. Authorization policy and tenant/organizational scope.
6. API request, response, error and versioning contract.
7. Frontend integration, localization and accessibility where applicable.
8. Unit, feature, negative, integration and regression tests.
9. Migration/recovery notes and observable failure behavior.
10. Exact candidate SHA, workflow URLs, known limitations and Owner gate recommendation.

Do not create abstractions without a current consumer. Do not implement business rules only in frontend code. Do not use binary floating point for money. Do not silently change API contracts, identifier uniqueness, authorization semantics, or authoritative data sources.

## 8. Verification and evidence policy

Every report must label claims as one of:

- **VERIFIED:** direct source or workflow evidence at a named revision supports the claim.
- **REPORTED:** documented in a prior report but not independently re-established in this check.
- **UNKNOWN:** insufficient evidence.
- **NOT RUN:** a check has not been executed.

Every code-bearing PR must record:
- Base SHA and candidate SHA.
- Changed paths and reason for each.
- Tests actually run, with pass/fail/skipped counts where available.
- Workflow links and their exact tested revisions.
- Known gaps and risks.
- Rollback/recovery considerations.
- Owner decision required next.

Do not repeat a successful broad audit unless a relevant source change invalidates it. Run only the targeted tests and existing regression gates relevant to the changed code.

## 9. Gate and authorization model

| Gate | Decision required | Permitted activity |
|---|---|---|
| A1 — Specification | Owner accepts scope, requirements and contracts | Read-only inspection and specification drafting |
| A2 — Read-only review | Owner accepts findings and file-specific plan | Targeted source/test inspection; no code mutation |
| A3 — Implementation | Owner authorizes bounded implementation | Changes only within approved paths and acceptance criteria |
| A4 — Verification | Owner authorizes verification scope | Targeted tests and relevant regression workflows |
| A5 — Release/deployment | Separate explicit Owner authorization | Merge/deployment/production actions within the authorization |

A merge authorization applies only to the PR explicitly identified by the Owner. It does not automatically authorize deployment or unrelated changes.
