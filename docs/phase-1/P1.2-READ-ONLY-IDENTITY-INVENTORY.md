## 3. Architectural conclusion

1. Use the existing Core User as the account authority.
2. Introduce a separate natural-person profile record; do not replace or duplicate User authentication fields.
3. Prefer explicit nullable foreign keys from supported domain records to the profile over a polymorphic relationship table as the authoritative link. This preserves database referential integrity.
4. Preserve legacy `user_id`, `representative_user_id`, free-text governance names and external references during an additive migration period.
5. Keep account membership, shareholder ownership, employment, and governance authority governed by their existing services/policies.
6. Do not backfill by matching names, phone numbers or email. Existing records remain unlinked until deterministic evidence and an approved linking workflow exist.
7. The following physical schema proposal is a design for review, not an instruction to execute migrations.
