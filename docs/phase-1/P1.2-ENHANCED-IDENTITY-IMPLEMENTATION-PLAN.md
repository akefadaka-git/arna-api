## 4. Required database and domain contracts

- Public UUID is generated once, unique, immutable, non-login and never reused.
- Internal numeric ID may remain the relational key if this is the compatible repository pattern; UUID is the stable cross-system reference.
- At most one current User link per Person and at most one current Person per User, enforced by a database unique constraint and service checks.
- Domain FKs are nullable for additive rollout. Existing rows remain unlinked.
- A profile link never creates/reactivates a tenant membership, role, permission, login credential, shareholder ownership, employment state, representation or governance authority.
- Legal-entity shareholder records cannot link to a natural-person profile; a representative is distinct from the shareholder.
- Every link/unlink/relink is authorized, transactional, auditable and safe under concurrent requests.
- No contact/national-ID/KYC claim is stored until purpose, verification, access, encryption/key handling, retention and deletion/anonymization are approved.
- No automatic matching, merge or backfill. Any later reconciliation is a separate design and execution gate.

## 5. Regression test matrix

| ID | Test | Required assertion |
|---|---|---|
| DB-01 | Clean install | Migrations install in correct dependency order on supported MySQL. |
| DB-02 | Migration discovery | Every new migration is discovered exactly once; no duplicate domain/root copies. |
| DB-03 | UUID invariants | UUID generated, unique, immutable and serialized consistently; malformed/duplicate value rejected. |
| DB-04 | FK/index contract | All FKs target correct tables; nullability, indexes and delete actions match approved contract. |
| ID-01 | Account cardinality | One User cannot be current on two people; one person cannot have two current Users. |
| ID-02 | Link/unlink/relink | Revocation preserves history; authorized relink works; old relationship is no longer treated as current. |
| ID-03 | No implicit account | Creating a person does not create or enable a User or credentials. |
| TEN-01 | Missing tenant | Operations requiring tenant scope fail closed. |
| TEN-02 | Cross-tenant link | Actor cannot link/unlink records outside authorized tenant/domain scope. |
| TEN-03 | No global discovery | No endpoint or query path enumerates profiles across tenants without separately approved authority. |
| AUTH-01 | No privilege inheritance | Person/account/domain link cannot grant membership, role, permission, ownership, employment or governance authority. |
| SH-01 | Shareholder type | Natural person can be linked when authorized; legal entity cannot; representative remains distinct. |
| EMP-01 | Employee compatibility | Employee number uniqueness, active state, rehire/history and existing User relationship remain correct. |
| GOV-01 | Governance compatibility | Position, appointment, term, status, overlap and decision authority remain governed by existing policies. |
| AUD-01 | Audit atomicity | Link mutation and required event commit or roll back together; event contains actor, tenant where applicable, action, target, reason and request ID without secrets. |
| CON-01 | Same User race | Two independent MySQL connections compete to link one User to different people; exactly one succeeds and state remains consistent. |
| CON-02 | Same Person race | Two independent MySQL connections compete to link different Users to one person; exactly one succeeds. |
| CON-03 | Retry/conflict | Duplicate request, stale state and uniqueness/deadlock conflict return safe deterministic outcomes without duplicate events. |
| REG-01 | Auth regression | Core User provider and login identifier resolver contracts remain unchanged. |
| REG-02 | Existing domains | Existing tenant, shareholder, governance, employee and loan suites pass or failures are classified against the candidate SHA. |
| PRIV-01 | Claim data minimization | Unapproved claims cannot be written or exposed; raw secrets/identifiers do not appear in logs/events. |
| API-01 | Resource exposure | Unauthorized requests fail safely; responses include only approved fields; no internal audit payload leaks. |

MySQL concurrency results must identify the workflow/run, commit SHA, database engine/version and relevant test output. A passing SQLite test or static assertion is not a substitute.

## 6. Migration rollout and recovery

1. Approve final schema and exact file manifest.
2. Implement additive schema and contracts on a dedicated branch/PR; preserve unrelated changes.
3. Run static/lint/schema-discovery tests, then clean-install MySQL tests.
4. Run domain regressions and independent-connection concurrency tests.
5. Review exact diff, CI workflows, test output, audit behavior and failure recovery.
6. Keep new FKs nullable and application compatible with unlinked existing rows.
7. Deploy schema before code that requires it only under a separately approved release plan.
8. Do not run backfill in this unit. Any later backfill requires dry-run report, deterministic matching evidence, unresolved-conflict report, reconciliation, forward-fix/recovery plan and separate explicit authorization.
9. Do not merge the PR or deploy without separate explicit Owner authorization.

Database rollback may be unsafe after new writes exist. The implementation must document whether rollback is truly reversible or whether forward-fix is the only safe recovery. Do not promise a destructive down migration that loses linked history.

## 7. Definition of implementation complete

- source and migration inventory is refreshed at the candidate SHA;

- unresolved failures, limitations and unverified production-engine behavior are explicit;
- no unapproved PII, global discovery, backfill, merge, production DB action, merge or deployment occurred;
- Owner receives a concise evidence report and a separate decision request for the next gate.
