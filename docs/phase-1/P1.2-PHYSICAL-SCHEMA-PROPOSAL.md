# ARNA OS P1.2 — Physical Schema Proposal

**Document ID:** ARNA-P1.2-SCHEMA-001  
**Version:** 0.1.0  
**Status:** Owner review required — proposed physical design only  
**Baseline:** `3fba10b58755ce6414cff83e789cecda718fc23e`  
**Companion inventory:** [P1.2 Read-Only Identity Inventory](P1.2-READ-ONLY-IDENTITY-INVENTORY.md)

## 1. Recommendation

Use a **global, minimal `people` table for natural persons**, with explicit nullable foreign keys from the existing domain tables that need a canonical person relationship. Keep the existing Core User, Employee, Shareholder, and Governance Membership records and their domain semantics. Do not introduce a polymorphic relationship table as the authoritative identity link.

This is an additive proposal. No migration or source code has been created by this document.

## 2. Proposed physical shape

### 2.1 `people` — canonical natural-person profile

Proposed columns:

| Column | Type / constraint | Purpose |
|---|---|---|
| `id` | BIGINT primary key | Stable internal person key |
| `public_id` | UUID/ULID, unique, non-login | Non-sequential external reference where APIs need one |
| `first_name_am` | nullable string | Amharic given name |
| `father_name_am` | nullable string | Amharic father's name |
| `grandfather_name_am` | nullable string | Amharic grandfather's name |
| `first_name_en` | nullable string | English given name |
| `father_name_en` | nullable string | English father's name |
| `grandfather_name_en` | nullable string | English grandfather's name |
| `user_id` | nullable FK to `users.id`, unique, `nullOnDelete` | At most one currently linked account per person; one account can belong to at most one profile |
| `is_active` | boolean, default true | Profile lifecycle flag; does not activate/deactivate the User account |
| `created_at`, `updated_at` | timestamps | Record lifecycle |
| `deleted_at` | nullable timestamp | Soft-delete marker only; not account revocation or domain deletion |

Notes:
- A unique index on nullable `user_id` permits multiple profiles without an account while preventing an account from being actively linked to multiple profiles.
- The account link is the current relationship only. Every link, revoke, and relink must be written to the existing append-oriented `audit_logs` table within the same transaction, using a stable action slug and old/new values plus metadata for reason and target. Confirm the audit writer and transaction behavior during implementation design.
- Do not store password, PIN, MFA secret, recovery code, tenant grants, share quantity, employment status, or governance authority in `people`.
- Contact details, verification, date of birth, national identifiers, and sensitive identity documents are **not included in the first schema**. Each needs a separate purpose, validation, privacy/retention rule, and Owner approval before storage.
- The table is global to provide stable identity across tenants. Global person search/list endpoints are out of scope. Reads must be authorized through a permitted tenant context and a domain relationship; no cross-tenant profile discovery by default.

### 2.2 Additive domain foreign keys

Add a nullable `person_id` FK to `people.id` and a tenant/person index to each of these existing tables:

| Table | Proposed addition | Required domain rule |
|---|---|---|
| `employees` | nullable `person_id` FK; index `(tenant_id, person_id)` | Link only through Employee service. Preserve `user_id`, employee number, active state, soft deletion and history. Do not assume rehire/cardinality rules without reviewing the full HR contract. |
| `shareholders` | nullable `person_id` FK; index `(tenant_id, person_id)` | Only natural-person (`individual`) shareholder records may be linked to a Person Profile. Legal entities keep `person_id = NULL`. Preserve separate `user_id` and `representative_user_id`; representative is never the shareholder identity. |
| `governance_memberships` | nullable `person_id` FK; index `(tenant_id, person_id)` | Keep membership dates, position, term, appointment, status, free-text names and external reference. A Person Profile link alone grants no governance authority. |

All new domain FKs should use restrictive deletion behavior or equivalent safe semantics rather than cascading deletion of domain history. The exact FK delete action must be reconciled with existing retention/legal requirements before implementation. The profile should normally be deactivated or unlinked, not hard-deleted.

The current nullable `user_id` fields remain during the compatibility period. Where both `person_id` and `user_id` are set, the owning domain service must enforce consistency with the linked Person Profile's current `user_id`. Do not silently infer or backfill `person_id` from `user_id`.

### 2.3 No new authoritative polymorphic link table

Do not use `(target_type, target_id)` as the authoritative relationship between a person and domain records; it cannot enforce a real FK to every target type. Explicit `person_id` FKs preserve referential integrity and make domain queries and migration behavior inspectable.

The existing `audit_logs` schema already supports actor `user_id`, optional `tenant_id`, action, resource type/ID, old/new values, request ID and metadata. It is a candidate for recording link lifecycle events, subject to confirmation that the existing audit writer supports the needed transactional guarantees and does not log excessive personal data. If those guarantees cannot be met, propose a dedicated append-only audit table before coding rather than silently weakening the audit requirement.

## 3. Migration sequencing proposal

The sequence below is logical, not a committed migration plan. Recheck migration timestamps and provider discovery against the target branch immediately before implementation.

1. **Schema migration A — create `people`:** after `users` exists; create table and unique nullable `user_id` FK.
2. **Schema migration B — add `employees.person_id`:** additive nullable FK and index.
3. **Schema migration C — add `shareholders.person_id`:** additive nullable FK and index.
4. **Schema migration D — add `governance_memberships.person_id`:** additive nullable FK and index.
5. Use one authoritative migration copy in the repository's established migration discovery arrangement. Existing Shareholder discovery tests require the schema migration to be in `database/migrations` when it is a flat/root schema migration; do not duplicate the same migration under a domain folder.
6. Add discovery tests proving each new migration is discovered exactly once and the dependencies are ordered correctly.
7. Add schema contract tests for FK targets, uniqueness, nullability and delete behavior.
8. No backfill in these schema migrations. Existing rows remain unlinked.

Migration ordering and names must be finalized from the exact branch's complete migration inventory; this proposal intentionally does not create files or reserve timestamps.

## 4. Link and lifecycle transaction contract

A future dedicated `PersonProfileService` should be the only write path for profile/account linking and unlinking. Domain relationships should be changed through the owning domain service or an explicitly coordinated service that calls it.

For account link/revoke/relink:
1. Resolve and authorize the actor and tenant context; fail closed when context is absent or conflicting.
2. Lock the Person Profile row and relevant account/link rows in a transaction.
3. Verify neither profile nor account has a conflicting active association.
4. Apply the link change, subject to unique FK constraints.
5. Write an audit event with actor, tenant (when applicable), action, target, old/new association and reason.
6. Commit as one unit. A failed audit write must roll back the relationship change.
7. Ensure caches/authorization snapshots are invalidated as required; the profile link itself must not create tenant memberships, roles, permissions, sessions, or ownership rights.

Concurrent attempts must be tested on MySQL using independent connections/processes. A SQLite-only result does not prove the unique-index race and lock behavior on production's database engine.

## 5. Compatibility and consistency rules

- The Core User remains the only authentication model.
- The current login identifier resolver continues to resolve login identifiers to a unique active User and tenant membership; Person Profile IDs are not login identifiers.
- A Person Profile link does not add, reactivate, or modify `tenant_memberships`.
- Existing shareholder direct-user and representative-user fields retain separate meanings.
- Existing governance membership `user_id`, free-text names and external reference remain available through a compatibility period; migration does not erase them.
- Existing Employee `user_id` and employment lifecycle remain intact.
- Profile creation does not automatically create a User, Employee, Shareholder, or Governance Membership.
- Name similarity, matching phone/email, or matching domain number may suggest manual review only; it must never automatically link or merge profiles.
- No existing row is backfilled in the first implementation unit. Any future backfill requires its own deterministic mapping, dry-run report, reconciliation, rollback/forward-fix plan and explicit authorization.

## 6. Required implementation and regression evidence

| Test group | Minimum evidence |
|---|---|
| Schema | All four FKs target `people.id`; nullable constraints and indexes correct; unique account link enforced |
| Account cardinality | One account cannot link to two profiles; one profile cannot link to two accounts; concurrent attempts leave one valid state |
| Tenant isolation | Cross-tenant reads and mutations denied; no global profile enumeration; missing/mismatched tenant fails closed |
| Lifecycle | Link → revoke → relink; old relationship no longer authorizes; history retained; audit event written transactionally |
| Authorization | Profile association does not grant tenant membership, roles, permissions, shareholder rights, employee state, or governance authority |
| Shareholder | Individual profile link allowed; legal-entity profile link rejected; representative remains separate; existing direct-user uniqueness retained |
| Employee | Employee number uniqueness and historical records retained; link changes do not silently change active status |
| Governance | Existing membership, term, appointment, position and audit invariants remain; profile link cannot grant authority |
| API | Resource exposure minimized; unauthorized list/detail/create/link/revoke calls denied; equivalent 404 handling where required |
| Migration | Clean install, exact-once discovery, correct ordering, and reviewed rollback/forward-fix plan |
| App | Amharic-first labels/errors, bilingual fallback, narrow viewport, keyboard navigation and focus checks |
| Regression | Existing auth, tenant, shareholder, governance and employee identifier suites pass on one exact candidate SHA |

## 7. Open risks before implementation

1. **Global profile privacy:** a global identity table creates cross-tenant exposure risk. Service authorization, query boundaries, response filtering and no-global-search behavior must be tested explicitly.
2. **Legacy identity ambiguity:** existing User, Employee, Shareholder and Governance rows may refer to the same person, different people, or representatives. No automatic data merge is safe.
3. **Employee rehire/cardinality:** the current schema does not prove whether one person can have multiple employee records per tenant over time. Do not add a uniqueness constraint on `(tenant_id, person_id)` until this policy is decided.
4. **Governance duplicate identity:** free-text name and external reference are not reliable unique identifiers. A profile link is explicit and auditable.
5. **Audit atomicity:** existing audit table shape appears adequate, but the exact writer/transaction contract needs source inspection before it is relied on for identity-link changes.
6. **FK delete semantics:** domain history must survive; exact restrictive/nulling policy must be confirmed with migration and service behavior.
7. **Contact and KYC data:** excluded from initial schema pending separate privacy and business requirements.

## 8. Proposed acceptance decision

Approve this as the physical schema direction only if you accept:
- one global natural-person `people` table;
- unique nullable `people.user_id` for the current account link;
- nullable explicit `person_id` FKs on employees, natural-person shareholders, and governance memberships;
- preservation of all existing User/domain links during compatibility;
- no automated backfill, no generic polymorphic authoritative link table, and no account/tenant/role/ownership/authority inheritance;
- additive migrations and MySQL concurrency/tenant-isolation verification before P1.2 closure.

**Status remains proposal only.** This document does not authorize schema or application changes, backfills, tests on production data, merge, or deployment.
