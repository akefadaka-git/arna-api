**Baseline inspected for the initial inventory:** `3fba10b58755ce6414cff83e789cecda718fc23e`

**Companion:** [Read-Only Identity Inventory](P1.2-READ-ONLY-IDENTITY-INVENTORY.md)

## 1. Decision and scope

The target is an enhanced, production-oriented, globally stable identity registry for **natural persons** across ARNA, while keeping authentication, tenant access, employment, share ownership, representation and governance authority separate.

A globally stable identifier means an immutable ARNA-issued UUID for the person record. It does not prove a civil/legal identity, authorize access, or permit cross-tenant discovery. The initial release will not perform automatic identity matching, bulk backfill, merge, or global profile search.

This is a design proposal only. No schema, application, test or production-data changes are authorized by this document.

## 2. Target architecture

Separate responsibilities into:
1. **Person registry:** canonical natural-person record and immutable global UUID.
2. **Account association:** current account link with database-enforced cardinality and a durable link lifecycle audit trail.
3. **Identity claims:** optional identifiers only when a specific purpose, verification policy, access policy and retention rule are approved.
4. **Domain relationships:** explicit foreign keys from employee, natural-person shareholder and governance records to a person.
5. **Audit and authorization:** existing tenant/security policy plus transactional event recording; identity linkage never grants privileges.

Do not introduce a generic polymorphic link table as the authoritative link. Legal entities remain represented in their existing domain records until a separate legal-party model is approved.

## 3. Proposed physical structures

Final types, names, indexes and foreign-key actions must be checked against the exact implementation branch, Laravel conventions, MySQL version and existing migration providers before coding.

### 3.1 `people` — canonical natural-person registry

| Field | Proposed contract |
|---|---|
| `id` | Existing-project-compatible numeric primary key for efficient internal joins; immutable once created. |
| `public_id` | Required, unique, immutable UUID generated by a cryptographically secure application/database-supported method; non-login and safe to expose only where authorized. |
| `first_name_am`, `father_name_am`, `grandfather_name_am` | Nullable Amharic display names; Unicode-safe collation/length and validation. |
| `first_name_en`, `father_name_en`, `grandfather_name_en` | Nullable English display names. |
| `user_id` | Nullable unique FK to canonical Core User for the **current** account association; preserve account lifecycle separately. |
| `status` | Constrained lifecycle state, e.g. active/inactive/restricted, with explicit transition rules; not an employment or account status. |
| `created_at`, `updated_at` | Standard timestamps. |
| `deleted_at` | Optional soft-delete marker only if retention policy supports it; no cascading deletion of historical domain records. |

**UUID storage decision:** use the project's proven Laravel/MySQL UUID representation after confirming its existing conventions. Prefer a native 16-byte representation if it can be supported consistently by models, migrations, API serialization and tooling; otherwise use a canonical 36-character UUID with a compatible binary/case-stable collation. Do not mix representations. Keep the immutable UUID unique regardless of internal primary-key choice.

Names are descriptive attributes, not unique keys. Do not require global uniqueness of names or use them as identity proof.

### 3.2 Current account association and lifecycle history

Keep a nullable unique `people.user_id` for the current association in the first implementation unless source review reveals a safer compatible pattern. This provides database-enforced maximum cardinality of one current User per Person and one current Person per User.

In addition, create an append-oriented `person_identity_events` or equivalently named domain audit structure **only if** the existing audit writer cannot reliably provide the required transactional semantics. Its proposed event contract includes:
- immutable event ID;
- person internal ID and stable public UUID reference;
- event type (created, account linked, account unlinked, identifier verified/revoked, restricted/reactivated);
- actor User ID where available and tenant context where applicable;
- event time, reason code, request/correlation ID and outcome;
- minimal before/after references needed for accountability, avoiding secrets and unnecessary personal data.

A separate event table must not duplicate an existing reliable audit system without justification. Before implementation, inspect the audit model/writer, transaction boundaries, retention, access controls and event integrity. If the existing audit writer can atomically persist the event with the identity change, reuse it with stable event slugs and a tested contract. A failed mandatory audit write must roll back the link mutation.

The current `people.user_id` value is the authoritative current association; historical events must not be treated as current authorization. Link and unlink operations must lock relevant rows in a transaction and rely on unique constraints as the final concurrency guard.

### 3.3 Optional identity claims — gated, not an automatic data collection mandate

Use a separate `person_identity_claims` structure only for identifiers explicitly approved for a business purpose. Candidate fields:
- internal claim ID and `person_id` FK;
- controlled claim type;
- issuer/namespace where applicable;
- protected normalized value or keyed digest for uniqueness/lookups where appropriate;
- verification state, verified-at, verification method/provenance;
- valid-from/valid-until and revoked-at;
- created/updated timestamps.

**No identifier types are enabled merely by adding this table.** Before storing phone, email, national ID, passport, date of birth, KYC evidence or other sensitive identifiers, approve each type's purpose, validation, uniqueness scope, verification method, encryption/key management, access policy, retention and deletion/anonymization requirements. Do not log raw claim values. A hash alone is not always sufficient for low-entropy identifiers; choose a keyed digest or encryption design based on threat model and lookup needs. Claims do not automatically become login identifiers.

### 3.4 Explicit domain relationships

Add nullable `person_id` foreign keys and appropriate tenant/person indexes to:
- `employees`;
- `shareholders`;
- `governance_memberships`.

Rules:
- Employee history and employee number uniqueness remain governed by the HR contract. Do not impose one employee row per person per tenant until rehire and concurrent/overlapping employment rules are confirmed.
- Only natural-person shareholder rows may link to a Person Profile. Legal-entity rows keep `person_id` null. Preserve `user_id` and `representative_user_id` as distinct concepts.
- Governance membership, appointment, position, term and authority remain separate. Profile association cannot grant governance rights.
- Preserve existing nullable User links, names, external references and domain status fields during the compatibility period.
- When a domain row has both `person_id` and `user_id`, the owning domain service must validate consistency under the approved policy. Never silently infer a person link from a User ID.

Use restrictive or otherwise explicitly safe FK deletion semantics. The exact delete action for every FK must be validated against current migrations, domain retention and the repository's established patterns. Never cascade-delete domain history because a profile is deactivated.

## 4. Tenant security and data minimization

The global registry is an internal identity anchor, not a globally searchable directory.

- Authorize every read and write through a validated tenant context and an allowed domain relationship or explicitly granted platform-level permission.
- Missing, inactive, conflicting or unauthorized tenant context fails closed.
- Do not expose global list/search endpoints in the first implementation.
- Avoid returning internal numeric IDs, claim values, audit metadata or relationship details unless the resource contract explicitly requires them.
- Do not allow profile UUIDs to act as bearer secrets or authorization credentials.
- Separate any tenant-specific profile attributes from global core identity if future requirements require differing visibility.
- Do not store passwords, PINs, MFA secrets, recovery codes, sessions, tenant grants, financial data, share quantities, employment status or governance authority on the person record.
- Define correction, restriction, retention and deletion/anonymization behavior before production use. Legal/audit retention may require deactivation or redaction rather than physical deletion.

## 5. Migration and rollout sequence

Migrations are additive and have no backfill.

1. Re-inventory the current branch's complete migration tree, schema providers, audit writer, model conventions and all references to employee/shareholder/governance User links. Confirm current `main` and branch heads.
2. Finalize the UUID representation, lifecycle states, FK delete actions, audit design and identity-claim purpose gate.
3. Migration A: create `people` after `users`; include UUID, approved minimal names/status and unique nullable current `user_id` association.
4. Migration B: add nullable indexed `employees.person_id`.
5. Migration C: add nullable indexed `shareholders.person_id`.
6. Migration D: add nullable indexed `governance_memberships.person_id`.
7. Migration E: only if approved and needed, create the event/history structure or approved identity-claim table. Do not enable unapproved sensitive claim types.
8. Add schema/discovery contract tests proving each migration is discovered exactly once, in dependency order, with the intended constraints.
9. Deploy additive schema before code that depends on it; release code must tolerate existing null links. No data backfill in this unit.
10. Any later backfill is a separately authorized operation with dry-run counts, deterministic evidence, exception report, reconciliation, recovery plan and explicit execution approval.

Use the single authoritative migration location required by existing repository discovery tests. Do not create duplicate copies under domain directories.

## 6. Transaction and concurrency contract

The only supported mutation path for account/profile linkage must be a dedicated authorized service, coordinated with domain services where needed.

1. Resolve actor and tenant context; fail closed on absent or conflicting context.
2. Validate target profile/account and the operation's authorization.
3. Begin a transaction and lock rows in a consistent order.
4. Check current associations and lifecycle state.
5. Update the current association using database constraints as the final guard.
6. Write required audit/event record in the same transaction.
7. Commit; invalidate affected caches/sessions/authorization snapshots where the actual architecture requires it.
8. On uniqueness conflict, deadlock or stale state, return a safe deterministic conflict and retry only where idempotency and transaction semantics make retry safe.

Test independent MySQL connections/processes competing to link the same User to two people and two Users to one person. Prove exactly one valid association remains, losing requests fail safely, no partial audit/business state survives, and repeat requests behave predictably. SQLite-only tests are insufficient evidence for MySQL locking/index behavior.

## 8. Acceptance criteria before P1.2 closure

- [ ] Immutable UUID uniqueness and stable serialization verified.
- [ ] No authentication or tenant authorization is derived from person linkage.
- [ ] One-current-account cardinality is enforced by the database and tested under concurrency.
- [ ] Explicit domain foreign keys are valid, nullable, indexed and have reviewed deletion behavior.
- [ ] Legal-entity shareholders cannot be assigned a natural-person profile.
- [ ] Account link → unlink → relink preserves history and cannot restore stale permissions.
- [ ] Audit write and link change are atomic; failure tests prove rollback.
- [ ] Tenant isolation covers read, list, detail, create, link, unlink and conflict responses.
- [ ] No sensitive claim type is collected without an approved purpose and protection/retention contract.
- [ ] Existing login resolver and Core User contract remain unchanged unless separately approved.
- [ ] Employee rehire/cardinality and shareholder/governance domain invariants are preserved.
- [ ] All migrations are discovered once and clean-install in the correct order.
- [ ] Relevant regression suites pass on one exact candidate SHA; failures are reported, not hidden.
- [ ] Independent-connection MySQL race tests pass.
- [ ] Production rollout/recovery limitations are documented; no production DB or deployment work without separate authorization.

## 9. Decisions that must be resolved before schema implementation

1. Confirm UUID storage representation based on repository conventions and MySQL performance/compatibility.
2. Confirm permitted lifecycle states and who may restrict/reactivate a person.
3. Inspect whether existing audit infrastructure meets atomicity and append-only requirements; add a dedicated event table only if necessary.
4. Decide whether any identity-claim type belongs in the first release. Default: none until separately justified and approved.
5. Confirm FK deletion/retention behavior and employee rehire/cardinality rules.
6. Confirm if a profile needs tenant-specific display/contact attributes; default: no global discovery and no sensitive contacts in initial schema.
7. Revalidate every path and migration dependency on the current branch before creating any implementation files.
