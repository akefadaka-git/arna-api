## 1. Gate objective
Establish an evidence-backed, testable contract for authentication, tenant resolution, tenant membership, authorization, and security-sensitive request handling before bounded implementation changes are proposed.

This document is not evidence that controls pass at runtime. Source inspection and existing test names are not substitutes for execution against the reviewed commit.

## 4. Security invariants
### Tenant context
- Every tenant-scoped request must resolve one canonical, active tenant from an explicitly supported source.
- Missing, malformed, ambiguous, inactive, deleted, or mismatched tenant context fails closed.
- Explicit tenant identifiers and tenant subdomains must follow one documented precedence rule; no silent fallback may change the tenant.
- Request-scoped tenant state must not leak across requests or tests.
- Authentication does not itself prove tenant membership.

### Authentication and identity
- Protected endpoints require a valid supported credential; invalid, expired, revoked, or malformed credentials are rejected.
- Identity resolution must use the intended canonical user model consistently across Sanctum, auth provider, controllers, policies, and relationships.
- Tenant context must be validated before tenant-dependent authorization or data access.
- Login and recovery paths must resist credential stuffing, enumeration, and unbounded notification generation without exposing account existence.
- Do not change password, PIN, MFA, recovery, or identifier policy in this gate unless a specific approved contract and targeted tests require it.

### Authorization
- Tenant membership and role/permission checks must be evaluated against the resolved tenant, not a caller-supplied untrusted tenant value.
- Model-aware policies must remain effective; raw permission abilities must fail closed when no applicable grant/definition exists.
- A permission granted in tenant A must not authorize the same operation against tenant B.
- Public and diagnostic routes must have explicit, reviewed data-minimization contracts.
- Authorization errors must not disclose internal model, tenant, credential, or stack details.

### Rate limiting and errors
- Login, registration, password-reset, email-verification, and other abuse-sensitive routes need explicit limits appropriate to their threat model.
- Rate-limit keys must not allow trivial bypass by changing between user and IP dimensions; trusted-proxy assumptions must be explicit.
- A rate-limit response must be a real 429 with retry guidance and the canonical sanitized API envelope.
- Production errors must not disclose stack traces or secrets.

## 5. Minimal implementation sequence
1. **P1.1-A — Route/middleware truth table:** enumerate effective routes, middleware, auth requirement, tenant requirement, authorization mechanism, rate-limit coverage, and intended public/diagnostic exception. Reuse the existing route audit; update only where the current tree differs.
2. **P1.1-B — Identity-model resolution:** trace `config/auth.php`, Sanctum provider/token model, login controller, route model imports, user relationships, and tests. Record one intended model path and concrete evidence before proposing changes.
3. **P1.1-C — Tenant fail-closed regressions:** cover missing/invalid/inactive tenant, mismatched explicit tenant vs subdomain, cross-tenant membership denial, request-context reset, and no data leakage.
4. **P1.1-D — Authorization regressions:** cover allowed and denied raw abilities, model policies, tenant-specific grants, unauthenticated calls, and default-deny behavior.
5. **P1.1-E — Abuse/error regressions:** verify throttling is attached to intended routes, IP/user key behavior is defensible, proxy trust is configured deliberately, and 429 uses the expected envelope.
6. **P1.1-F — Verification and evidence:** run only the targeted existing/new tests and the relevant repository workflows once, after reviewing the diff. Record exact SHA, commands, counts, results, and workflow URLs.

## 6. Candidate test matrix
| Area | Required positive case | Required negative/regression cases |
|---|---|---|
| Tenant resolver | Supported identifier resolves canonical active tenant | Missing, malformed, reserved, inactive/deleted, ambiguous, mismatch |
| Context lifecycle | Context available during intended request | State cleared between requests; no singleton leakage |
| Membership | Active member accesses tenant-scoped resource | Non-member, revoked member, user from another tenant denied |
| Auth model | Login/token resolves expected platform identity | Model mismatch, invalid/revoked token, deleted user |
| Policies | Authorized operation succeeds | Unauthorized model action denied; tenant A grant does not cross to B |
| Raw abilities | Explicit tenant-scoped grant succeeds | Missing grant/definition and unauthenticated call denied |
| Rate limits | Intended route returns normal response under limit | Repeated login/recovery calls yield 429 with retry metadata |
| Error contract | Sanitized canonical success/error envelopes | No stack traces, secrets, or cross-tenant existence leaks |

Tests must assert observable HTTP/service behavior where practical; static source-contract checks alone do not prove runtime enforcement.
