# Finance Phase 1 — Production Readiness and Go-Live Checklist

**Document status:** release-gate specification  
**Scope:** Finance Phase 1 general-ledger integrity  
**Database target:** MySQL 8.0 / InnoDB  
**Application runtime:** PHP 8.3 / Laravel 12

This document distinguishes verified source and CI behavior from operational readiness. A green CI run on a disposable database does not establish that a production environment has been backed up, migrated, seeded, reconciled, or approved for live transactions.

## 1. Phase 1 integrity controls

| Control | Required invariant | Evidence gate |
|---|---|---|
| FIN-1.01 | Tenant/entity-scoped request idempotency and immutable source-event identity/version; matching retries converge; changed payloads conflict | MySQL uniqueness constraints, service regressions, source-event resolver tests |
| FIN-1.02 | Journal posting, reversal, and synchronous audit persistence are atomic; posted journals and audit history are immutable | Transaction rollback regressions and MySQL/SQLite database guards |
| FIN-1.03 | Duplicate submissions, period close versus posting, and direct line writes versus posting serialize safely | 60 controlled independent-connection MySQL races, two arrival orders per race |
| FIN-1.04 | Journal, period, account, reversal, and report access remain tenant/legal-entity scoped | Composite foreign keys, scoped service queries, adversarial service and direct-SQL regressions |
| FIN-1.05 | ISO dates, period boundaries, journal numbers, descriptions, and DECIMAL(20,4) values are validated before persistence | Boundary and tenant/entity uniqueness regressions |
| FIN-1.06 | Posting revalidates active entity, base currency, open period/date, line/account ownership, account status, cash-equivalent classification, and balance | Posting-time service checks and database posting guards |

The Finance domain CI workflow is expected to verify a clean migration, InnoDB engines, required uniqueness indexes, integrity triggers, the full Finance test directory, and the bounded concurrency protocol at one exact commit SHA.

## 2. Production environment prerequisites

Before deploying any Finance schema or enabling live posting:

- Confirm the target is a supported MySQL 8.0 release and all Finance ledger tables use InnoDB.
- Confirm the application runtime satisfies PHP 8.3 and the locked Composer platform requirements.
- Confirm the application database principal has the privileges needed to create the required triggers during migration. Do not grant routine application traffic privileges to alter schema or triggers.
- Confirm the production connection uses the intended database, tenant resolution fails closed, and all Finance routes execute under the expected authentication, tenant, and permission middleware.
- Confirm transaction isolation, connection pooling, lock-wait timeout, deadlock monitoring, and backup retention meet the organization's operational policy.
- Do not point the disposable CI harness at a production or shared environment. It creates test tenants and journals and is restricted to an isolated test database.

## 3. Migration and recovery gate

1. Take a verified, restorable database backup and record its timestamp and recovery point.
2. Test restoration to an isolated environment before the production migration window.
3. Review the exact release commit and migration diff independently.
4. Run the migration plan against a production-like clone and verify trigger creation, composite foreign keys, unique indexes, and table engines.
5. Apply migrations during an approved maintenance window with a named operator and rollback/recovery owner.
6. Re-run the read-only schema verification and Finance smoke checks after migration.
7. Retain migration output, schema evidence, exact commit SHA, operator, start/end timestamps, and any exceptions.

Do not assume that a generic migration rollback is safe for ledger data. For a failed production migration, stop writes and use the approved restore or forward-fix plan after assessing whether any ledger transactions have been committed.

## 4. Chart of accounts and opening balances

- The canonical CoA v1.0.0 seeder is opt-in and is not part of the default seeding flow.
- Do not execute it until the Owner approves the legal entities, chart mapping, control-account ownership, and seeding window.
- Reconcile any pre-existing account codes before seeding; non-system accounts must never be overwritten.
- Opening balances are deliberately not generated by this Phase 1 work. They require independently verified source balances, approved cut-off dates, and a separately authorized migration/reconciliation plan.
- Do not permit live posting until the account register and required control-account ownership have been reconciled for every legal entity.

## 5. Explicitly disabled capabilities

The following are not production-enabled by Phase 1:

- Foreign-currency journals and FX revaluation. The ledger remains ETB base-currency only.
- Automatic subledger posting from unregistered source domains. Shareholder, Wallet, and Loan source mappings have a guarded resolver; other external source types remain fail-closed until their owning domains provide authoritative event identity and tenant/entity eligibility contracts.
- Automatic opening-balance generation or default CoA seeding.
- Any deployment, production database mutation, or merge authorization.

These are deliberate controls, not defects to bypass through configuration or direct SQL.

## 6. Operational controls required for go-live

- Establish named roles for journal preparation, posting approval, period closure, source-mapping approval, and emergency recovery; enforce segregation of duties where required by policy.
- Monitor failed idempotency conflicts, rejected source mappings, period-close rejections, posting failures, deadlocks, lock-wait timeouts, and audit-write failures.
- Alert on missing or altered Finance triggers, disabled InnoDB tables, missing unique indexes, or unexpected migration drift.
- Confirm audit retention, access restrictions, backup protection, and restore testing.
- Reconcile trial balance, balance sheet, income statement, and cash-flow outputs against approved opening data before accepting live transactions.
- Define incident response and ledger correction procedures. Correct posted history through authorized reversals and new journals, never by editing or deleting posted ledger rows.

## 7. Go-live acceptance record

Production release requires all of the following evidence, recorded against the exact release SHA:

- [ ] Independent source review and approved PR.
- [ ] Full Finance tests and exact-commit MySQL migration verification pass.
- [ ] All 60 controlled MySQL concurrency races pass on the target-compatible MySQL version and isolation level.
- [ ] Tenant, legal-entity, permission, and direct-database adversarial checks pass.
- [ ] Production-like migration rehearsal and verified backup restore pass.
- [ ] Chart of accounts and control-account ownership are approved and reconciled.
- [ ] Opening balances are separately verified and approved, or the entity is explicitly blocked from live posting until they are.
- [ ] Monitoring, alerting, audit retention, and incident/rollback ownership are active.
- [ ] Owner approves the production release and deployment window.

**Current boundary:** this document defines the production gate; it does not certify a live environment. No production database, deployment, or merge is authorized by the CI results alone.
